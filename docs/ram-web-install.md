## 首刷流程

用户流程可保持为：启动临时 OpenWrt → 打开“系统／备份与更新” → 上传专用安装包 →
核对版本和保留配置选项 → 确认安装 → 自动重启。

可复用官方 LuCI 上传、SHA-256 显示、校验确认和重连界面；无需另外开发整套网页。
后端需要该板专用的 `platform_check_image`、`platform_do_upgrade` 和配置恢复逻辑。
包内应提供受限格式的内核、压缩根镜像、板型/布局/版本/长度/哈希清单，并补齐官方
fwtool 支持设备元数据。上传阶段保存压缩包；刷写时流式解压到块设备，不能把数 GB
解压结果留在 `/tmp`。上传大小及解压长度均需检查。

写入前重新核对精确安装内核、板型、eMMC 容量、p6/p9 起点与大小、未挂载/无 swap、
其他分区及 SD 只读。镜像板型或布局不匹配时禁止继续，也不提供“强制升级”绕过。
沿用已准备安装器的顺序：p9 → fsync/清块缓存/读回 → p6 → 同样校验 → 恢复配置 →
重启。不能直接照搬通用 `emmc_upgrade_tar`：它会先清零内核开头、执行尾部/overlay
处理，且其配置保存方式不适合当前直接可写 ext4 根布局。

紧凑首刷镜像可只写约 1 GiB，首次启动后扩展 ext4 到 p9 的固定容量；不需要调整
分区表或 `blkdevparts`。需要加入匹配架构的 resize2fs/必要库、限定设备身份和容量，
并验证扩容及后续重启。不对未用区做直接安全擦除承诺；这种方式可能留下不可见的
旧文件数据，需要与当前完整覆盖方案明确区分。当前正在安装的镜像不在本轮研究中替换。

## 后续网页升级的边界

首刷时根在 RAM；安装后根在 p9。后续不能从正在挂载的 p9 上直接运行 `dd` 覆盖它。
官方第二阶段能停服务、复制程序并切到 ramfs，但采用 lazy unmount 不足以证明块设备
已完全释放；该板升级处理器必须确认所有 p9 挂载、swap、loop/DM 引用已消失。必要时
使用已支持的临时系统重启路径，而非放开 mounted-write 保护。

当前 Docker 数据与系统同在 p9 的 `/opt/docker`。正常重启保留与刷固件保留是两件事：
重写根镜像会覆盖 Docker 数据，LuCI“保留配置”也不等于备份 Docker 镜像和卷。
首刷方案可实现，但后续保留 Docker 数据的升级方案还需另设计/备份；这次研究不改
分区布局，也不宣称已有无损应用数据升级能力。

要提高真实写入速度，需要另一个限定 p6/p9 的多扇区实现，检查整个请求范围、CMD25/
停止命令和错误完成路径，并单独验收。继续单线 PIO 时仍有总线带宽上限；不承诺仅改
网页就达到厂商驱动速度。可先使用紧凑镜像减少写入量，再评估多扇区，避免无依据地
一次改动总线宽度、高速模式和 DMA。

## 与 HiTool 的关系

本地 HiTool 包含 Hi3798MV100-CA 芯片定义及 HiBurn eMMC 烧写文档。文档支持
按选定分区烧写，且使用引导器 `mmc write`；这可以绕过当前 Linux 单扇区路径。
但文档的“已有 boot、网口烧写”模式只对部分芯片/具有烧写检测配置的 boot 开放，
不能仅凭存在 CA 芯片定义就认定当前 fastboot 已兼容。需确认本机命令和配置、仅选择
p6/p9，保留 CA fastboot，不采用裸烧或重建分区表作为默认流程。

网页 RAM 安装更适合该项目后续用户操作；HiTool/引导器可作为另一个候选恢复入口。
两条路径都还未完成独立刷写验收。
