> 历史阶段记录：以下结论仅适用于所列日期、profile 和镜像；文中的“未完成”描述当时边界。当前能力与使用方法见 [STATUS](../STATUS.md)，阶段导航见[验证索引](README.md)。

Method: local CLI at 115200, 8N1, no flow control, receive only. The user normally
rebooted existing Hinas. The CLI transmitted no bytes and did not interrupt
autoboot. Raw bytes and decoded text stay in ignored local `evidence/`.

legacy image. This is evidence for the current Hinas boot path. It does not

Bootloader help, transfer/boot commands and DTB handoff were not queried.

Those are emitted by the existing bootloader without host input. The capture
does not establish whether that stock path performs an OTP operation; no OTP
command or security-state modification was requested or sent by this project.

## Original kernel and userspace observations

- Linux `4.4.35_ecoo_81082668` starts all four CPUs.
- RAM total 1048576 KiB; initial available 736572 KiB; reserved 45764 KiB;
  CMA reserved 266240 KiB. These are initial boot figures and need not equal
  the later SSH MemTotal reading.
- CMA: 256 MiB at `0x2ec00000` and 4 MiB at `0x3fc00000`.
- Original command line again identifies p9 as the ext4 root, `mem=1G`,
  `mmz=ddr,0,0,256M` and `vmalloc=500M`.
- The board USB device on `1-2` enumerates at high speed. The original kernel
  warns that bulk endpoints `0x03` and `0x83` have invalid maxpacket 64. This
  is an additional descriptor/driver compatibility observation, not proof of
  why no RDA interface driver is bound.
- Ubuntu reports unsupported proc mount option `hidepid=invisible` under this
  old kernel. `smartmontools.service` fails. `networking.service` waits more
  than five minutes, displays a timeout extension from 5m03s to 6m33s, then
  fails. The system nevertheless reaches its normal login prompt. No service
  configuration was changed.
